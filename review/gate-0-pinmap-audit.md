## Verification results (what was checked and passed)

* **Pin numbers (all 64):** every pin number/name in pinmap section 2 matches [PIN]: VBAT 1, PC13-15 2-4, PH0/PH1 5/6, NRST 7, PC0-PC3 8-11, VSSA 12, VDDA 13, PA0-PA3 14-17, VSS 18, VDD 19, PA4-PA7 20-23, PC4/PC5 24/25, PB0-PB2 26-28, PB10/PB11 29/30, VCAP_1 31, VDD 32, PB12-PB15 33-36, PC6-PC9 37-40, PA8-PA13 41-46, VCAP_2 47, VDD 48, PA14/PA15 49/50, PC10-PC12 51-53, PD2 54, PB3-PB7 55-59, BOOT0 60, PB8/PB9 61/62, VSS 63, VDD 64. There are 51 I/O pins (count of `Type="I/O"` = 51), and the package has no VREF+ pin. The author's count is correct.
* **AF numbers (all):** match [AF]: USART1/2/3 = AF7 (PA9/PA10, PA2/PA3, PC10/PC11); UART4/5, USART6 = AF8 (PA0/PA1, PC12/PD2, PC6/PC7); SPI1 = AF5 (PA5/6/7); SPI2 = AF5 (PB13, PC2, PC3); SPI3 = AF6 (PB3/4/5); I2C1 = AF4 (PB8/PB9); TIM3_CH3/CH4 = AF2 (PB0/PB1); TIM2_CH3/CH4 = AF1 (PB10/PB11); TIM8_CH3/CH4 = AF3 (PC8/PC9); TIM1_CH1 = AF1 (PA8); OTG_FS_DM/DP = AF10 (PA11/PA12).
* **ADC channels:** PC0 = ADC123_IN10, PC1 = ADC123_IN11, PC5 = ADC12_IN15 [PIN]. ADC1 is the BF default instance (`adc.h:28-29`, `ADC_INSTANCE ADC1`).
* **DMA (every stream/channel in pinmap 3.1/3.2 and the config comments):** all correct. [BF-DMA] / [AP-DMA]:
  SPI1_TX (2,3,3)/(2,5,3); SPI1_RX (2,0,3)/(2,2,3); SPI2_TX (1,4,0); SPI2_RX (1,3,0); SPI3_TX (1,5,0)/(1,7,0); SPI3_RX (1,0,0)/(1,2,0); ADC1 (2,0,0)/(2,4,0); TIM1_CH1 (2,6,0)/(2,1,6)/(2,3,6); TIM2_CH3 (1,1,3); **TIM2_CH4 BF order (1,7,3), (1,6,3)**, so BF opt0 = S7 and opt1 = S6 (`dma_reqmap_mcu.c:445`; INAV has the same order, ArduPilot lists the same two streams in the other order); TIM3_CH3 (1,7,5); TIM3_CH4 (1,2,5); TIM8_CH3 (2,2,0)/(2,4,7); TIM8_CH4 (2,7,7).
  **Answer to the TIM2_CH4 vs TIM3_CH3 question:** PB11 opt0 (DMA1 S7 ch3) and PB0 (DMA1 S7 ch5) would clash on DMA1 Stream 7. The config pins `dma pin B11 1` = DMA1 S6 ch3, so **there is no clash**. The DMA1 and DMA2 stream maps in pinmap 3.1/3.2 are each stream used at most once, as claimed.
* **BF allocation order:** confirmed in `init.c`: `motorDevInit` (l.545), then `adcInit` (l.673), then `ledStripInit` (l.774), then `spiInitBusDMA` (l.988, `USE_SPI_DMA_ENABLE_EARLY`, before `motorPostInit`). The author's statement is right. ADC needs an explicit dmaopt, because the default `ADC1_DMA_OPT` is `DMA_OPT_UNUSED` (`common_defaults_post.h:155`) and `adc_stm32f4xx.c:302-304` then gets no DMA. `dma ADC 1 1` is therefore required and correct.
* **Bidirectional DShot:** all motor pins are CHx, not CHxN. Timer DShot with telemetry reuses `motor->dmaRef` for input capture (`pwm_output_dshot.c:89-196`), so no extra streams are needed. `dshot_burst = OFF` is required with telemetry (`pwm_output_dshot.c:81`). `dshot_bitbang = OFF` is valid (`settings.c:860`, `USE_DSHOT_BITBANG` is defined for F405 in `common_pre.h:57`). The author's bit-bang/DMA2 rationale matches `bus_spi.c` (comment on errata 2.1.10).
* **TIMER_PIN_MAP occurrence indices:** match `fullTimerHardware`: PB0 = TIM1_CH2N(1), TIM3_CH3(2); PB1 likewise; PC8/PC9 = TIM3(1), TIM8(2); PB10, PB11 and PA8 each have only one entry.
* **CLI syntax/names:** every `resource` name exists in `resource.c` (MOTOR, LED, LED_STRIP, BEEPER, SERIAL_TX/RX, I2C_SCL/SDA, SPI_SCK/SDI/SDO, ADC_BATT/CURR/RSSI, PINIO, FLASH_CS, OSD_CS, GYRO_CS, GYRO_EXTI, USB_DETECT). `dma SPI_SDO/SPI_SDI/ADC` exist (`cli.c:5322-5327`). Every `set` name exists in 4.5 `settings.c`/`parameter_names.h`, including `gyro_to_use` (FIRST/SECOND/BOTH) and `i2c1_clockspeed_khz`. Feature names are valid (`cli.c:233`). Serial function masks are correct: MSP 1, GPS 2, RX_SERIAL 64, ESC_SENSOR 1024, VTX_MSP 131072 (`serial.h:37-53`).
* **Polarity claims:** beeper `IOWrite(io, inverted ? on : !on)` (`sound_beeper.c:85`), so `beeper_inversion = ON` drives HIGH for beep. This is correct for an N-FET gate. Status LED `IOWrite(io, on ? inverted : !inverted)` (`light_led.c:92`), so non-inverted drives LOW = on for a sink LED. Correct. PINIO 129 = OUT_PP | INVERTED: init drives HIGH (`drivers/pinio.c`), the box task is enabled only when a mode range exists (`piniobox.c:73`), so the VTX is on by default. Correct. `USE_PINIOBOX` is auto-enabled (`common_post.h:646-648`).
* **Drivers present:** BMP390 chip-id 0x60 accepted by the BMP388 driver (`barometer_bmp388.c:52,277`). IIS2MDC is register-compatible with LIS2MDL (WHO_AM_I 0x4F = 0x40, address 0x1E; `compass_lis2mdl.c`), and `USE_MAG_LIS2MDL` is auto-enabled (`common_post.h:102`). ICM42688P, BMI270, W25N01G and multi-gyro are all in `common_pre.h`.
* **Electrical (passed):** PA13/PA14 are kept free. USB uses PA11/PA12. The two gyro INTs are on EXTI4 and EXTI14 with no other EXTI user. PC13-15 carry only inputs or a static CMOS enable. PB2/BOOT1 has a 10k pull-down (BOOT0=1, BOOT1=0 selects system memory). PA15 (JTDI, pull-up at reset) is a good default for an active-low CS. PB4 (NJTRST pull-up) on MISO and PB3 (JTDO, floating) on SCK are harmless while FLASH_CS is pulled up. The VBUS divider 10k/15k gives 3.15 V at 5.25 V, and still more than 2.5 V with BF's internal pull-down. The VBAT divider 10k/1k is OK with `vbat_scale 110`. VCAP 2 x 2.2 µF, VBAT pin tied to VDD with 100 nF, and VDDA 1 µF + 100 nF are all correct.

## Findings

| ID | Severity | Finding | Evidence | Recommended fix |
|---|---|---|---|---|
| G0-01 | **MAJOR** | **Requirement "4 extra motor/servo pads if timers allow" is not met (2 provided), and the shortfall is avoidable.** Section 5 says only 2 pins are left. But one pin (PC13) goes to VBUS detect, which is **not a requirement**, and one UART TX (PC12) is an unused "spare TX pad" while ESC telemetry needs RX only. Timers are available (TIM4, TIM5 unused). Rearranging gives 4 extra outputs without dropping any required feature: (a) CAM_SEL → PC13 (static CMOS input, ideal for a low-drive pin), BEEPER → PB2 (active-high gate; the BOOT1 pull-down also keeps the buzzer silent), which frees **PB7 = TIM4_CH2 (AF2)**; (b) ESC TLM → UART4_RX PA1, which frees **PA0 = TIM5_CH1 (AF2)**, and UART5 PC12/PD2 becomes a full spare (HD "R2" can go to PD2). PB7/PA0 are PWM/servo only: TIM4_CH2 = DMA1 S3 ch2 clashes with SPI2_RX, and TIM5_CH1 = DMA1 S2 ch6 clashes with M2. The requirement says "motor/servo", so servo-only pads satisfy it. | requirements.md "4 extra motor/servo pads"; pinmap s.5; [PIN] PB7 TIM4_CH2, PA0 TIM5_CH1; [AF] PB7 TIM4_CH2=AF2, PA0 TIM5_CH1=AF2; [BF-TIM] l.75 `DEF_TIM(TIM5, CH1, PA0)`, l.107 `DEF_TIM(TIM4, CH2, PB7)`; [BF-DMA] TIM4_CH2 (1,3,2), TIM5_CH1 (1,2,6) | Adopt the remap (or an equivalent one), add `resource MOTOR 7 B07` / `MOTOR 8 A00` (or SERVO), `timer B07 AF2`, `timer A00 AF2`, and `dma pin B07 NONE` / `dma pin A00 NONE`. Note in section 5 that S7/S8 are PWM/servo only. If the owner prefers to keep VBUS detect, get an explicit written waiver of the requirement. A waiver is required either way, since 2 of 4 does not meet it as written. |
| G0-02 | MINOR | **`resource USB_DETECT 1 C13` does nothing at runtime in BF 4.5, and the signal is only used for debug.** `usb_io.c` initialises the pin from the compile-time macro `IO_TAG(USB_DETECT_PIN)` (default `NONE`), not from the PG `usbDev_t.detectPin` that the CLI `resource` writes. On a stock STM32F405 build plus CLI paste, detection is therefore inactive. The only caller of `usbCableIsInserted()` found was `DEBUG_SET(DEBUG_USB, …)` (`tasks.c:136`). The pinmap's claim "used by BF for MSC / USB connected logic" is not supported. | [BF] `usb_io.c` `usbCableDetectInit()`; `pg/usb.c:37`; `cli.c:5135`; `common_defaults_post.h:80-81`; `fc/tasks.c:136` | Supports G0-01: drop VBUS detect and reuse PC13. If it is kept, correct the pinmap text and rely on `USB_DETECT_PIN` in config.h, not the CLI resource. |
| G0-03 | MINOR | **ROM DFU can be hijacked by UART activity (unverified, since AN2606 was not downloadable).** The F4 system bootloader scans USART1 (PA9/PA10), USART3 (PB10/PB11 and, per the auditor's recollection, possibly PC10/PC11) and CAN2 (PB5/PB13) as well as USB. **The GPS is on USART3 PC10/PC11, and requirements put the GPS on the 5 V rail, which is OR-ed from USB.** So with USB-only power, the GPS streams NMEA into PC11 during DFU. If PC11 is a bootloader pin, the loader can lock onto USART3 and USB DFU will not enumerate (a classic F4 FC symptom). PB5 (CAN2_RX) is flash MOSI and floats at reset. PB11 is M4 (ESC unpowered without battery, so OK). PA10 is fed by the HD VTX, which is on the 10 V rail and dead on USB power, so OK. | AN2606 STM32F40xxx section (not accessible); requirements.md 5 V rail feeds GPS + USB OR-ing; pinmap pins 51/52, 57 | Check AN2606. If PC10/PC11 are bootloader pins: swap GPS to a non-bootloader UART (e.g. UART4/UART6 per the G0-01 remap), or add a 10k pull-up on PB5 and a series 0 Ω / power-gate on GPS 5 V. At minimum, document "unplug GPS for DFU". Firmware DFU via BF `bl` (software jump) is unaffected. |
| G0-04 | MINOR | **Two IMUs share SPI1, and the BMI270 powers up in I2C mode.** BF detects gyro_1 (ICM-42688-P) before gyro_2 (BMI270) (`gyro_init.c:614-623`), and SPI CS preinit only drives CS high (`bus_spi_config.c:68-76`), so the BMI270 sees no CS rising edge until its own probe. During ICM probing, the BMI270 (I2C mode, SCx = SCK, SDx = MOSI) can see START-like patterns on SCK/MOSI and drive SDx (= MOSI) low on an address match, which corrupts ICM traffic. The risk is low, but it is a known Bosch shared-bus caveat. The pinmap does not address it. | BMI270 datasheet (`datasheets/BMI270_DS.pdf`, interface selection: switch to SPI on CSB rising edge); [BF] `gyro_init.c`, `bus_spi_config.c` | Bring-up test: cold-boot repeatedly and confirm both gyros are always detected. Mitigations: make the BMI270 gyro_1 (CS PA15 / EXTI PC14) so it is switched to SPI first, or add a firmware CS-pulse on PA15 in preinit. Optionally fit a pull-down/pull-up option footprint. |
| G0-05 | MINOR | **The HD-VTX "SBUS/R2" requirement is unresolved, and it reduces the spare-UART count.** R2 on PA1 (UART4_RX) leaves UART4 half-used, so only USART6 is a fully spare UART (requirement: "2 spare"). SBUS from DJI/Walksnail is inverted and F405 has no RX inversion, so an inverter is needed. | requirements.md HD VTX and 6 UARTs lines; pinmap s.8 item 1 | Owner decision. If R2 is required, accept "1 full + 1 half spare" in writing, or use the G0-01 remap (R2 → PD2/UART5_RX with inverter footprint + 0 Ω bypass). Add BF `serialrx_inverted`/`INVERTER` notes to the config. |
| G0-06 | MINOR | **"INAV compatible" (requirement) has no deliverable.** INAV's F4 timer table also lists TIM2_CH4 as `D(1,7,3), D(1,6,3)`, so an INAV target **must** use dmavar 1 on PB11, otherwise M1/M4 clash on DMA1 S7. INAV doesn't support dual gyro, and driver support for IIS2MDC/BMP390/ICM42688P/BMI270 should be confirmed. | requirements.md "Betaflight (and INAV) compatible"; [INAV] `timer_def_stm32f4xx.h:41` | Add an INAV `target.c`/`target.h` sketch with `DEF_TIM(TIM2, CH4, PB11, TIM_USE_OUTPUT_AUTO, 0, 1)`, ADC1 on DMA2 S4, and a driver checklist. |

The backup domain is kept alive by VBAT=VDD across resets, so any firmware that once enabled LSE/RTC (e.g. a non-BF test build) leaves the pins in oscillator mode until a power cycle or backup-domain reset. BF itself does not enable LSE. | RM0090 backup domain / LSE (not accessible; general F4 behaviour); pinmap pins 3/4 | Add a note for bring-up/test firmware: do not enable LSE; a power cycle clears it. ## Verdict

**FAIL**: 1 MAJOR (G0-01), 0 BLOCKER.

Pin numbers, AF numbers, ADC channels and the entire DMA plan (the area flagged as highest risk) were independently verified and are **correct**. The PB11 `dma pin B11 1` → DMA1 S6 choice is right and is required to avoid the DMA1 S7 clash with PB0. The Betaflight CLI is syntactically valid for 4.5. The fail is a requirement-coverage issue only: two more servo-capable outputs can be recovered by reusing the non-required VBUS-detect pin and the unused UART5 TX role. Fix G0-01, or get a written waiver from the requirement owner, then re-audit. G0-03 should be resolved against AN2606 before schematic capture.
